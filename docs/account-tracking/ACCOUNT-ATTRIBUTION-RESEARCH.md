# Forward-only account attribution

Research date: 2026-09-07. This note preserves the initial investigation and early POC follow-up. Claims about what was not implemented or agreed describe those snapshots. See [Account tracking](ACCOUNT-TRACKING.md) for accepted behavior, storage safeguards, and remaining native checks. This research concerns attribution after the saved tracking start; historical usage is displayed without account attribution.

## Finding

The persisted billed request contains usage and request correlation information, but no account identity. Correlating a request to its originating VS Code window and that window's authentication timeline can support attribution during a stable account period. It does not supply a direct record of the credential used for every request. Account switches, missing evidence, and persistent connections therefore need explicit handling and validation before describing attribution as reliable.

The most important unresolved case is continuing an existing chat after changing accounts. Copilot can reuse a WebSocket authenticated when the connection was first opened. Its connection reuse check does not compare the new authorization header. This is confirmed source behavior, not proof that the service bills the wrong account.

## What the source records

- A billed `llm_request` has the inference span's start time, duration, session ID, span ID, model, optional `responseId`, and optional `copilotUsageNanoAiu`. Its emitted attributes contain no GitHub login, account ID, or token identity. The session header contains extension and VS Code versions, not an account or window ID. See [request serialization, lines 1004-1063](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/chat/vscode-node/chatDebugFileLoggerService.ts#L1004-L1063) and [session header, lines 594-607](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/chat/vscode-node/chatDebugFileLoggerService.ts#L594-L607).
- `Logged in as <login>` is written before Copilot token exchange. `Got Copilot token for <login>` is written after successful exchange. Reading only the first message can mistake an attempted authentication for a successful token change. Cached tokens can be returned without another login message; token renewal also produces these messages. See [token acquisition, lines 55-96](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/platform/authentication/vscode-node/copilotTokenManager.ts#L55-L96).
- The HTTP fetch path obtains a Copilot token before passing it into the transport. The inference span begins inside the transport after token acquisition, and the token supplies authorization unless the endpoint owns its authorization. Therefore the billed span timestamp is not the time the user pressed Send, nor the time the completed row was discovered. See [token acquisition and dispatch, lines 220-246](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts#L220-L246) and [span creation and token use, lines 1034-1085](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts#L1034-L1085).
- The debug row's `responseId` comes from `result.requestId`. A successful result returns the caller's request ID, which may come from supplied `telemetryProperties.requestId` or `messageId` rather than a new UUID. The same value can therefore occur across model calls; it is not a guaranteed per-call key. See [ID selection, line 159](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts#L159), [span response ID, line 426](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts#L426), and [successful result, lines 1895-1906](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts#L1895-L1906).
- A retry can call `fetchMany` again and obtain another token. Assigning one account to an entire chat or outer user request would miss an account change between its individual model calls. See [retry, lines 893-910](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts#L893-L910).
- Debug files are scoped to workspace storage, with global storage as fallback. Existing sessions can be resumed from a previously resolved storage root. A debug file's location does not itself identify the current writer window. See [storage selection, lines 190-200](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/chat/vscode-node/chatDebugFileLoggerService.ts#L190-L200) and [session creation, lines 294-384](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/extension/chat/vscode-node/chatDebugFileLoggerService.ts#L294-L384).

## Cases that cannot yet be attributed reliably

1. **Continue an existing chat after switching accounts.** A WebSocket connection is reused when open, idle, and using the same model; that check does not compare authorization headers. Its map key is conversation ID plus connection ID. New headers only reach a newly created connection. The coordinating agent's installed-bundle search found no authentication-change listener closing these connections; `closeAll()` appeared only in manager disposal. This requires a real account-switch test before relying on the latest login for continued chats. See [reuse, lines 199-214](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/platform/networking/node/chatWebSocketManager.ts#L199-L214) and [key and cleanup, lines 263-276](https://github.com/microsoft/vscode/blob/a44adf7f53e00964ab890f9f8758a334f1fc15bc/extensions/copilot/src/platform/networking/node/chatWebSocketManager.ts#L263-L276). Server-side billing behavior remains untested.
2. **Switch accounts while requests or retries are active.** A request can finish after the displayed account changes; its completion time cannot establish which token sent it. A later retry can obtain a different token. Source establishes these distinct lifetimes, but the exact safe attribution boundary needs validation against a real switch. This does not mean every overlapping request must be unknowable: an unambiguous dispatch and authentication record could retain its original account.
3. **The originating window or its authentication timeline cannot be recovered.** Examples include a missing or truncated Copilot text log, starting observation without a recoverable successful account marker, or a request that matches no window or several windows. A record from another window cannot inherit the current window's account. These are evidence-loss conditions inferred from the separate request and authentication records, not failures observed in the current sample. Restarting or having several windows is not automatically a failure if the needed records remain and the match is unique.
4. **A login attempt is recorded but successful token acquisition is not established.** The pre-exchange login line alone does not establish which credential an in-flight or cached-token request used. A failed sign-in without a billed request does not create unattributed usage. Routine successful refresh for the same account is not an account switch.

In a newly observed window with a known account, no evidence gaps, no switches since the relevant transport was created, and an unambiguous request-to-window match, the source supports a defensible stable-account inference. It still is not an explicit account field attached by Copilot to the billed request. The distinction should remain clear in any later agreement about what the POC must prove.

## Local evidence supplied by the coordinating inspection

The inspected corpus covered Stable Code storage roots and `.jsonl` files no larger than 50 MiB. It was not an exhaustive inspection of every editor, profile, or JSON container. Within that scope it contained 657 JSONL files and 12,724 positive-credit rows. No account field appeared in the inspected row or attribute keys. A nested JSON-string inspection found one historical June 5 row with `requestOptions.metadata.user_id` containing `device_id`, `account_uuid`, and `session_id`; its `account_uuid` was empty, so it supplied no ownership evidence. Other inspected billed options lacked login or account identity. Of 1,867 distinct `responseId` values, 1,311 appeared more than once, consistent with the source's non-unique ID construction.

In the latest live snapshot, all 67 billed rows for today matched a request completion in exactly one retained window log when matching both `responseId` and completion time within two seconds. Each matched window had a successful account marker before the billed span and no different-account marker during it. All these billed spans belonged to the same anonymized account timeline. This demonstrates feasible correlation in the observed stable-account case, not switch safety, billing proof, or validation of the two-second tolerance. Logs were still growing during inspection.

At this research snapshot, no controlled tests covered billed requests across account switches, active-request switches, resumed WebSockets after switching, multiple windows using different accounts concurrently, or missing authentication-log segments. The accepted exclusion policy and remaining native checks now live in [Account tracking](ACCOUNT-TRACKING.md).

## POC follow-up, September 7

The findings above describe the initial research snapshot, before the user authorized implementation. The September 7 development preview introduced the local ledger and exclusions for requests around switches and chats that predate a switch. The ledger now runs in both development and installed windows; [Account tracking](ACCOUNT-TRACKING.md) describes current behavior. Historical usage files remain untouched.

The first manual test exposed two implementation bugs. Windows paths with `C:` and `c:` produced duplicate window evidence and billed entries. The MAI transport emitted a successful `ccreq` summary without the `request done` marker used by the initial sample. Neither was a missing authentication log.

The POC now deduplicates Windows path aliases, including previously saved entries. It also accepts a unique successful summary when model, start time, end time, and duration agree within 25 milliseconds. A summary must match exactly one billed request, and a billed request must match exactly one summary. This is a conservative correlation tolerance, not a documented Copilot guarantee. The same authentication and switch exclusions still apply. The installed Copilot bundle confirms that these summaries report the request logger's model and measured start/end interval. The observed MAI request differed by one millisecond.

A replay of a copy of the user's ledger with the retained window logs resolved all 48 saved requests without exclusions or pending evidence. Restarting against that copy preserved the totals. Regression tests cover path aliases, saved duplicates, summary ambiguity, model/time mismatches, delayed evidence, and summary persistence after log deletion. Real account-switch acceptance remains for the user to check.
